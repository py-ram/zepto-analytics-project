# Support Assistant

## Overview

This module implements a small retrieval-based support assistant for Zepto policy questions.

The application uses:

- Sentence Transformers for local text embeddings
- `all-MiniLM-L6-v2` as the embedding model
- ChromaDB for local vector storage and similarity retrieval
- LangGraph `StateGraph` for intent routing
- Pydantic for response validation
- FastAPI for the `/ask` API
- A deterministic `MOCK_LLM` path for the default execution

The default mode does not require an LLM API key or an external LLM call.

## Pipeline

### 1. Document Ingestion

`embedding.py` loads the eight policy documents:

```text
doc_01.txt
doc_02.txt
doc_03.txt
doc_04.txt
doc_05.txt
doc_06.txt
doc_07.txt
doc_08.txt
```

The files are stored in the `docs/` directory.

The `load_documents()` function reads the files and prepares the text for embedding.

---

### 2. Chunking

The `chunk_text()` function splits each policy document into smaller pieces.

This keeps the retrieved context manageable and allows ChromaDB to store individual chunks.

Each chunk receives an ID such as:

```text
doc_01_chunk_1
doc_01_chunk_2
```

The source document and chunk number are also stored as ChromaDB metadata.

---

### 3. Embedding

The project uses:

```text
all-MiniLM-L6-v2
```

from Sentence Transformers.

The model converts each policy chunk into a numerical embedding vector.

The embeddings are created locally.

---

### 4. ChromaDB

The embeddings and document chunks are stored in a local ChromaDB collection named:

```text
zepto_policies
```

The collection is created by `embedding.py`.

The database is stored in:

```text
support_assistant/db/
```

This directory is generated at runtime and is excluded from Git.

---

### 5. Intent Classification

The first LangGraph node is:

```text
classify_intent
```

The node uses a simple keyword-based heuristic to identify policy questions.

The keywords include:

- delivery
- return
- refund
- membership
- tracking
- cancel
- gift card
- support hours

If a policy keyword is found, the state is assigned:

```text
policy_question
```

Otherwise:

```text
general_question
```

---

### 6. LangGraph Routing

The application uses a LangGraph `StateGraph`.

The graph contains three required nodes:

```text
classify_intent
retrieve_and_answer
direct_answer
```

The routing is:

```text
classify_intent
       |
       +--------------------+
       |                    |
       v                    v
policy_question      general_question
       |                    |
       v                    v
retrieve_and_answer   direct_answer
```

This conditional routing is implemented using LangGraph conditional edges.

---

## Retrieval Node

The:

```text
retrieve_and_answer
```

node performs the following steps:

1. Converts the user question into an embedding.
2. Searches the ChromaDB collection.
3. Retrieves the top three relevant chunks.
4. Stores the retrieved source IDs.
5. Produces the response.

---

## Direct Answer Node

The:

```text
direct_answer
```

node handles questions that are outside the policy scope.

The deterministic response is:

```text
I can only answer questions about Zepto policies right now.
```

No retrieval is performed for this route.

---

# MOCK_LLM

The application defaults to:

```text
MOCK_LLM=1
```

This is the recommended assignment execution mode.

When mock mode is enabled, no external LLM API is called.

For policy questions, the response starts with:

```text
Based on the retrieved context:
```

and includes the highest-ranked retrieved context snippet.

For general questions, the fixed response is:

```text
I can only answer questions about Zepto policies right now.
```

---

## Optional Real LLM Mode

The application also contains an optional real-LLM path.

To enable it:

```text
MOCK_LLM=0
```

An API key is then required:

```text
OPENAI_API_KEY=your_key_here
```

The model can be selected using:

```text
OPENAI_MODEL=gpt-4o-mini
```

The default mock path does not require these variables.

---

# Structured Prompt

The optional real-LLM path uses a structured prompt containing:

- Role
- Context
- Task
- Format
- Length
- Negative constraint
- Few-shot example

The negative constraint tells the model:

```text
Do not use information that is not present in the supplied context.
```

This is intended to reduce unsupported policy answers.

---

# Response Schema

The API response follows this structure:

```json
{
  "answer": "...",
  "sources": [
    "doc_01_chunk_1"
  ],
  "confidence": 1.0
}
```

The fields are:

### `answer`

The response returned to the user.

### `sources`

The policy chunks used to produce the response.

### `confidence`

A numeric value between:

```text
0 and 1
```

The Pydantic model validates this range.

---

# Real-LLM Validation and Retry

When `MOCK_LLM=0`, the optional real-LLM path validates the returned JSON against the Pydantic response schema.

The process allows:

```text
Initial attempt
      ↓
Validation
      |
      +---- success → return response
      |
      +---- failure
              ↓
        correction prompt
              ↓
          retry #1
              ↓
        correction prompt
              ↓
          retry #2
```

This gives a maximum of three generation attempts.

# Limitations

This is a small assignment-oriented prototype.

The main limitations are:

- The intent classifier uses a simple keyword heuristic.
- The default `MOCK_LLM` path is deterministic rather than generative.
- ChromaDB is stored locally.
- The optional real-LLM path requires an API key.
- The system is not intended to be a production customer-support platform.
